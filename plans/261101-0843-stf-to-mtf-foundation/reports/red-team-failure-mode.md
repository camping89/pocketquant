## Finding 1: A restored or handed-over resting stop has no owner in the strategy, so it fills against the strategy's current view and the strategy EXIT never fires afterwards
- **Severity:** High
- **Location:** Phase 09, Open issue 3 and Task 09.4 steps 8-9; Phase 14, Task "Rules fixed here", steps 2, 4 and 5; plan.md design verdict "Resting stop trigger order"
- **Flaw:** Phase 09 keeps a pending stop across a handover (`stop()` calls `on_stop()` only) and rebuilds it in the next trader's paper broker (`broker.restore(rows, realized, stops)`). Nothing tells the strategy instance that a stop is resting. The only restore hook is `restore_direction`, which sets `_open_direction` and nothing else. Triple Screen keeps its stop state in `_armed`, which `on_start` clears (Phase 14 step 2) and `on_order_rejected("warmup")` clears during the warm-up replay. Phase 14 step 5 sets `_open_direction` on a fill only "on the armed side", so a fill with `_armed is None` leaves the strategy flat.
- **Failure scenario:** The paper subscription from D4 (`entry_type=stop, exit_mode=strategy`) has a buy stop resting. A deploy or VPS restart hands over. The new trader warms up (`_armed` set, then cleared by the warm-up rejection), takes over, and restores the stop into the broker. On the next entry bar the setup is gone, so Triple Screen decides "hold, no setup" (its "setup gone with `_armed` -> exit" branch needs `_armed`). No signal means no cancel-then-place, so the stale stop keeps resting. Later `fill_resting_stops` fills it. `on_order_filled` sees no armed side, `_open_direction` stays `None`, and in `strategy` mode (TP is `None`) the tide-flip EXIT is never emitted because the strategy thinks it is flat. The position lives until its SL. If the setup returns, the strategy emits a new entry, risk rejects it ("entry against an open position"), and `on_order_rejected` clears state again.
- **Evidence:**
  - Plan: Phase 09 step 8 "`stop()` replaces its `stop_strategy` loop ... calling `on_stop()` ... A handover keeps pending stops for the next trader."; step 9 "call `broker.restore(rows, realized, stops)`"; Phase 14 step 5 "a fill on the armed side (BUY for LONG) sets `_open_direction = _armed` ... `on_order_rejected` clears both".
  - `src/pocketquant/core/domain/strategy/strategy_service_interface.py:30-31`: `restore_direction` sets only `_open_direction`.
  - `src/pocketquant/engine/strategy/strategy_app_service.py:251` (`on_start` before replay), `:265-266` (every warm-up signal gets `on_order_rejected("warmup")`), `:271` and `:174` (only the direction is restored, at start and at take_over).
  - `src/pocketquant/app/roles.py:166` then `:203`: bootstrap warm-up runs in standby, before `engine.take_over()`; the stop is restored after the strategy state was built.
  - Flow trace: FAILED. Phase 09 tests `test_a_resting_stop_survives_a_takeover` and `test_a_handover_stop_keeps_the_pending_stop` assert only broker and order state, never the strategy's view.
- **Suggested fix:** Pick one rule and write it into Phases 09 and 14. Either (a) cancel every restored resting stop at take_over (the strategy re-places it on its next bar if the setup still holds; simplest, consistent with "every new signal cancels then places"), or (b) pass the restored pending side to the strategy (extend `restore_direction` to `restore(direction, pending_side)`) and make Triple Screen's `on_order_filled` set `_open_direction` from the fill side when `_armed` is `None`. Add a test: takeover with a resting BUY stop, setup gone on the next bar, then assert no fill can open a position the strategy does not know about.

## Finding 2: A stopped subscription keeps a live resting stop that can open a position, and an edit then silently deletes that position
- **Severity:** High
- **Location:** Phase 09, Task 09.4 steps 6, 8, 9; Phase 06, Task 06.3 step 3 and Task 06.4 step 2; Phase 11, Task 11.2 step 6
- **Flaw:** Three paths combine. (1) `fill_resting_stops` runs for every connected paper broker in `self._brokers.values()`, with no check that the subscription is running. (2) `take_over` restores stops for every loaded subscription id, running or not. (3) The reconcile loop calls `stop_strategy` only for an instance that is running, so a subscription that is already non-running in this process is never cancelled. Step 8 also leaves it ambiguous whether the new cancel sits inside the existing `if strategy.is_running:` block of `stop_strategy`.
- **Failure scenario:** The owner presses Stop while the trader is down or mid-handover (the D6 window, a deploy, a crash). The old trader's `stop()` kept the stop. The new trader bootstraps the subscription as loaded but not running (desired `stopped`), and take_over restores its stop. `_converge_one` sees desired `stopped` and not running and does nothing, so the stop is never cancelled. A later 1m bar fills it, and a position opens on a subscription the UI shows as stopped. `_on_order_filled` ignores the fill because the strategy is not running, so only the SL manages it. Separately, the edit guard runs in the api against Mongo (open position or pending order means 409). If the stop fills between that check and the trader's reload, `_ensure_instances` unloads the instance, and `unload_strategy` calls `drop_positions` and `PositionAppService.drop`. The position row is deleted with no trade.
- **Evidence:**
  - Plan: Phase 09 step 6 "for each distinct connected `PaperBrokerAdapter` in `self._brokers.values()`, call `await broker.fill_resting_stops(event)`"; step 9 "`stops = [o for sid in ids if (o := ...pending_stop(sid)) ...]`"; Phase 06 Task 06.4 step 2 comment "an edit is allowed only while stopped and flat, so dropping the stale instance loses nothing".
  - `src/pocketquant/engine/strategy/strategy_app_service.py:151`: `ids` is every subscription bound to the broker, not only running ones. `:297-298`: `on_stop` only `if strategy.is_running`. `:316-317`: unload drops broker positions and the tracker row. `:465`: a fill for a non-running strategy is ignored.
  - `src/pocketquant/engine/live/strategy_reconcile_app_service.py:53-57` (bootstrap starts only desired `running`), `:188-191` (`stop_strategy` only when `strategy.is_running`).
  - Flow trace: FAILED. "Stopping a subscription cancels its pending stop" holds only when the stop happens in the same process that holds the stop.
- **Suggested fix:** In `fill_resting_stops`, skip orders whose subscription is not running (the engine passes the running ids), or cancel the stops of non-running subscriptions at take_over. Make Phase 09 step 8 explicit: the cancel runs outside the `is_running` check, so `unload_strategy` always cancels the Mongo order. Add tests: (a) takeover of a stopped subscription with a SUBMITTED stop leaves no resting order; (b) the reload path refuses to unload while `PositionAppService.get(sid)` returns an open position.

## Finding 3: A manual close applied right after a takeover fills at the stored entry price, and D6 makes that the normal path
- **Severity:** High
- **Location:** Phase 09, Task 09.3 step 4 (`close_position`); Phase 11, Task 11.2 step 5; plan.md D6; Phase 17, Task 17.1 obs-3
- **Flaw:** Paper `close_position` prices the fill at `self._current_prices.get(symbol.upper(), pos.current_price)`. After a takeover, `_current_prices` is empty until the paper broker's own `_on_bar_completed` sees the next finest bar. `pos.current_price` is whatever the restored Mongo row holds, and the stored row's `current_price` is the entry price: only the paper broker's in-memory copy is marked per bar, and the tracker saves only on fills. The reconcile loop runs its first tick straight after take_over, before any bar.
- **Failure scenario:** The owner presses "Close at market" while the trader is down (D6: "runs when the trader holds the lease again"). The new trader takes over, the first `_reconcile` call applies the action at once, and `_fire_synthetic_exit` fills at the entry price. The `trades` row records a P&L near minus the commission, whatever the market did. For XAUUSD on a weekend restart, `_current_prices` stays empty for about two days, so every manual close in that window is mispriced. The Phase 17 obs-3 check tests only timing, so it passes.
- **Evidence:**
  - Plan: Phase 09 step 4 "The trigger is `self._current_prices.get(symbol.upper(), pos.current_price)`"; D6.
  - `src/pocketquant/core/domain/position/entities.py:69`: `current_price=entry_price` at open. `src/pocketquant/engine/execution/position_app_service.py:49-74`: the tracker saves on fills only.
  - `src/pocketquant/core/infra/brokers/paper/paper_broker_adapter.py:237-246`: `restore` deep-copies the rows and leaves `_current_prices` untouched. `:478`: the only live writer of `_current_prices`. `:503`: the per-bar mark is in-memory only.
  - `src/pocketquant/app/roles.py:203-206` (reconcile task created right after `take_over`); `src/pocketquant/engine/live/strategy_reconcile_app_service.py:65-67` (the first `_reconcile` runs before the first sleep).
  - Flow trace: FAILED. "closes at market" is not true until the first finest bar after a restart.
- **Suggested fix:** In `manual_action("close")`, return False (the action stays pending, as D6 allows) while the broker has no current price for the symbol: add a `has_price(symbol)` check, or let `close_position` return False when `_current_prices` has no entry. Add a test: restore a position, call `manual_action("close")` before any bar, and assert it stays pending and fills at the next bar's close.

## Finding 4: EXIT goes through the entry-only skip guards, and the rejection resets Triple Screen into thinking it is flat
- **Severity:** High
- **Location:** Phase 09, Task 09.4 step 4 (no change to the `_on_bar_completed` guards); Phase 14, step 5 ("`on_order_rejected` clears both")
- **Flaw:** `_on_bar_completed` skips any signal on a stale, gapped, non-successor or in-flight bar and calls `_notify_rejected`. The code comment says these guards exist for entries. Phase 09 routes EXIT through the same path without an exemption. Triple Screen's `on_order_rejected` clears `_open_direction` and `_armed` whatever the reason.
- **Failure scenario:** A held LONG in `exit_mode=strategy` (the D4 setting). The tide flips on a 15m bar that carries `gap=True` (more than 60 trading seconds with no ticks, for example a feed reconnect). `reason="gap"` drops the EXIT, and `on_order_rejected("gap")` sets `_open_direction = None` while the position stays open. From then on the strategy's "position held" branch never runs, so no EXIT is ever sent again. The position exits only at its SL. It is the same with `stale`: Phase 07 adds a Mongo read (`_refresh_context`) inside the handler before the decision, which raises the chance of a late decision.
- **Evidence:**
  - `src/pocketquant/engine/strategy/strategy_app_service.py:360-362`: comment "An entry on a stale, gapped or non-successor live bar ... is skipped". `:401-421`: the guards apply to every signal and call `_notify_rejected`.
  - `src/pocketquant/engine/market_data/app_services/bar_app_service.py:34` (`_GAP_AFTER_S = 60.0`), `:181-182,198-199,263-267` (how `gap` is set).
  - Plan: Phase 14 step 5 "`on_order_rejected` clears both"; Phase 09 Task 09.4 does not touch `:401-421`.
  - Flow trace: FAILED. "EXIT means go flat" does not hold on a gapped or stale bar.
- **Suggested fix:** In `_on_bar_completed`, let `Direction.EXIT` bypass the `stale`, `gap` and `successor` guards (going flat is never a look-ahead risk). Keep the lease checks. In Phase 14, make `on_order_rejected` clear only `_armed`, never `_open_direction` (the position source is the fill events). Add a test: an EXIT on a `gap=True` bar still closes the paper position.

## Finding 5: The backtest skips the SL on the EXIT bar and on the stop-fill bar, which biases D3 toward `entry_type=stop, exit_mode=strategy`
- **Severity:** Medium
- **Location:** Phase 09, Context "The same-bar worst-case SL check is dropped" and Task 09.4 step 6; Phase 16, Tasks 16.2-16.4 (the owner picks the live set from these runs)
- **Flaw:** A backtest streams only the entry interval. Strategies are subscribed before the paper broker. (a) On an EXIT bar the engine closes at the bar close before the broker checks the SL, so an SL touched inside that bar is never taken. (b) A stop filled from bar N+1's range gets `opened_at` = sim time = bar start = `occurred_at`. The `fresh` rule then skips its SL check for the rest of N+1. That is up to one entry bar (1h in the `1h,4h,1d` set) of unchecked adverse range. Live checks SL/TP on 1m bars, which the trader publishes before the entry bar in the same batch, so live has neither gap. A market entry has no such window: it fills at the close.
- **Failure scenario:** On the `1h,4h,1d` set, a stop fills at 10:20 inside the 10:00 bar, and the bar's low pierces the SL at 10:40. The backtest does not stop out at 10:00. At 11:00 the bar opens above the SL and never revisits it, so the trade survives in the backtest and loses in live. The six-run table then favours the stop/strategy setting, and D4 deploys it.
- **Evidence:**
  - `src/pocketquant/engine/backtest/backtest_app_service.py:106,109,121`: price set to the bar close, sim time = bar start, `occurred_at = bar.datetime`.
  - `src/pocketquant/core/infra/brokers/paper/paper_broker_adapter.py:383` (`opened_at=get_current_time()`), `:479` (`fresh` skip), `:484` (closed positions skipped), `:106-111` (the broker subscribes last).
  - `src/pocketquant/engine/backtest/backtest_sandbox_app_service.py:138` (the engine subscribes first); `src/pocketquant/engine/market_data/app_services/bar_app_service.py:38-45,113-126` (live publishes 1m first in each batch).
  - Flow trace: FAILED for the A4/A10 claim that the backtest behaves like live at bar boundaries.
- **Suggested fix:** Before the strategies decide on a backtest bar, run the SL/TP check for positions opened before that bar (the same "before strategies" move Phase 09 makes for stops). For a stop filled on bar N+1, check the SL against the part of N+1's range beyond the fill (worst case). If the owner keeps the drop, Phase 16's metrics table must state the bias next to each stop/strategy row before the owner picks the live set.

## Finding 6: Two closes of one position can reverse it, because the identity re-check passes for a closed position
- **Severity:** Medium
- **Location:** Phase 09, Context ("`_fire_synthetic_exit` ... re-checks the position identity") and Task 09.3 step 4; Phase 11, Task 11.2 step 5
- **Flaw:** A closed paper position stays in `_positions` under its key. `_fire_synthetic_exit` checks only `self._positions.get(key) is not pos`, so a second exit of the same, now closed, object passes. `_execute_fill` treats a closed position as absent and opens a new one on the exit side. Today only one SL/TP exit can target a position. This plan adds two concurrent exit paths: manual close from the reconcile task, and strategy EXIT.
- **Failure scenario:** Two paper subscriptions on one symbol share one paper broker. On one 1m bar both hit SL. The broker collects `[posY, posX]` and fires them in sequence. While posY's callbacks await (Mongo saves, bus publish), the reconcile task applies a manual close of X: posX closes. The bar handler then fires posX's SL exit. The identity check passes, and a SELL with no live position opens a SHORT. That is exactly the case the new doc text in Phase 09 Task 09.5 step 1 calls rejected ("an opposite market order as the close, which opens a position when an SL fill lands first").
- **Evidence:** `src/pocketquant/core/infra/brokers/paper/paper_broker_adapter.py:335-339,358-360` (closed means absent, so a new position opens), `:493-494` (sequential awaited exits after the lock), `:547-551` (identity-only check); `src/pocketquant/app/roles.py:205` (reconcile runs as its own task). Flow trace: FAILED for "paper closes under its own lock ... never opens or reverses one".
- **Suggested fix:** In `_fire_synthetic_exit`, skip when `pos.is_closed` as well as on an identity mismatch, and return False. Add a test: fire two exits of one position with an await between them, and assert one fill and no new position.

## Finding 7: `fill_resting_stops` opens positions without the lease gate
- **Severity:** Medium
- **Location:** Phase 09, Task 09.4 step 6; plan.md design verdict "Resting stop trigger order"
- **Flaw:** A stop fill is an entry, but the trigger runs at the top of `_on_bar_completed` on every connected paper broker and never reads `trading_until`. The engine's invariant is "No entry leaves while `trading_until` is None or past". On a lost lease, the old trader marks itself lost with up to 5 s of lease left, then `engine.stop(5)` waits up to 5 s before it disconnects the brokers. Its brokers keep filling stops in that window.
- **Failure scenario:** The old trader loses its lease. The new holder acquires it, `load_pending_orders` reads the stop as SUBMITTED, and `restore` re-arms it. The old process fills the same stop on a bar in its tail window: the order is saved FILLED and a position row is written. The new trader then fills its stale copy on the next bar and writes a second position row for the same subscription.
- **Evidence:** `src/pocketquant/engine/strategy/strategy_app_service.py:90-92,504,513-534` (the lease gate exists only in `_process_signal`), `:126-139` (wait, then disconnect); `src/pocketquant/app/roles.py:106-110,216-227`. Flow trace: FAILED for "No entry leaves while trading_until is None".
- **Suggested fix:** In the engine loop, call `fill_resting_stops` only when `trading_until is not None and now < trading_until`. A missed touch during a handover is the same accepted gap as a missed signal. Add one test with `trading_until = None`.
