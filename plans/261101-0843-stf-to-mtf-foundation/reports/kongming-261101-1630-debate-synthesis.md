## 1. Verdicts per disagreement

**D1 Closed-HTF-bar instant: C1 wins (entry-bar START), stated as "the HTF bucket closed strictly before the entry bar's close".**
- Fact: in a backtest the simulation clock is the bar start and the event has no `bar_end` (`engine/backtest/backtest_app_service.py:109-123`). An instant equal to `bar["timestamp"]` (= `bar_start`) needs no clock in any path, so live, warm-up and backtest use one pure filter `b.datetime + step <= entry_bar_start`.
- Governance: `docs/governance/no-look-ahead-rules.md:7-8` allows only bars "fully closed by the close of the bar it decides on" and forbids joining an HTF bar to the LTF bars inside its own bucket. With `<=` on the entry END, the last entry bar of a bucket (for example 10:45-11:00 with the 10:00 1h bar) would receive its own bucket's bar, which line 8 forbids. Entry START excludes it. Check 1 (`:19`) holds: the first entry bar of a new bucket has `start == previous bucket end`, so it sees exactly the previous bucket's close.
- Live data: `sync_1m` runs at second 12 (`engine/market_data/app_services/sync_jobs.py:738`) with a 100-minute cascade lookback (`:410`), so the previous bucket is final in Mongo about 12-19 s after its end. Under the START rule the first event that can read it fires at `bucket_end + entry_step` (>= 60 s), a margin of >= 40 s with no wait. `_STALE_AFTER_S["1m"] = 10` (`engine/strategy/strategy_app_service.py:43`) stays intact; C2's own risk table admits its 20 s wait turns every 1m rollover bar into a `stale` skip.
- Equivalence: because C3 requires every higher interval to be a multiple of the entry interval, C3's rule `HTF_end <= entry_end - 45 s` admits exactly the same bars as the START rule for every entry interval >= 1m. Drop the constant and its measurement gate (spike G4 stays as evidence only, not as a knob).
- C2's "final" check `updated_at >= datetime + step` is wrong for session symbols: XAUUSD trading stops at 20:57:59 every weekday (`core/infra/calendars/exness_session_calendar_adapter.py:58-59`), so every XAUUSD 1d bucket and every 20:00 4h bucket has `updated_at` about 21:00:12, before its bucket end, and would be dropped forever. `updated_at` is also wall clock, not simulation time (`core/infra/persistence/repositories/bar_repository.py:45,68,94`). No task, no wait, no `event_bus.py:28-38` concern remains.
- Keep from C3 (D-B): cache a miss only when the previous HTF bucket is present or has no trading minutes; otherwise re-query on the next entry bar and log WARNING once per (symbol, interval, window). Drop C1's "trusted at bucket_start + 20 s" second read: in live the first read already happens >= 60 s after the bucket end, so the rule is always true there.
- Residual, documented: a cascade later than about 40 s (worker handover, slow Exness REST) can cache a partial previous bucket for one HTF window. No new code; the data-lag monitor exists. State it as negative knowledge in `docs/system-architecture.md`.
- Trap none of the three fixed: the warm-up wait at `strategy_app_service.py:240-248` fires only when the stored entry bars miss the last closed one. For a cascaded entry interval (15m and up) at hh:00:05 the partial last bar is already stored and passes `_closed_bars` (`:285-289`), so no wait happens and a partial entry bar plus a partial HTF prefetch are replayed. Fix in Phase 07: wait to second 20 whenever `now.second < _WARMUP_READY_SECOND` (a start is rare; 20 s is cheap). Comment the WHY.
