# Advice: ES1! / NQ1! / YM1! index futures in PocketQuant via TradingView, generalized by asset class

Date: 2026-09-21 (Asia/Saigon). Workflow: `ak:advise --agent`. Interview: 5 questions + 2 confirmations. Reframing v2 confirmed by the user.

## Confirmed reframing

**Problem.** PocketQuant is hardwired to one 24/7 crypto venue. DI binds exactly one `IDataProviderPort` (`BinanceAdapter`) and one `IRealtimeQuoteProviderPort` (`BinanceWebSocketAdapter`); the sync cron, cascade aggregator, annualization table and paper broker all assume continuous trading and price x quantity units. The user wants `ES1!`, `NQ1!`, `YM1!` (CME/CBOT continuous front-month E-mini index futures) for charts, live paper trading, and higher-timeframe, forward-accumulating backtests, sourced from TradingView through `tvdatafeed` or an equivalent scraper, delivered through (a) an asset-class model that drives session, annualization and contract math inside the existing pipeline, and (b) provider resolution keyed by asset class and provider id, so that a third provider, or a second provider for one asset class, is one adapter plus one config entry.

**Requirements.**
- R1 `AssetClass` enum on `Symbol` (replaces the free-string `asset_type`), binding annualization basis and contract-spec shape; per-symbol contract values (ES $50, NQ $20, YM $5 per index point; ticks 0.25 / 0.25 / 1.0).
- R1b `TradingSchedule` is persisted data stored alongside the asset class; 24/7 is simply crypto's schedule. It carries the exchange IANA timezone, weekly session open/close, daily maintenance halt, weekend closure, a holiday hook, and the session-day boundary used for 1d/1w bucketing. A future asset class is a new enum member plus a new schedule record, not new branching.
- R2 Provider registry/resolver replacing the single DI binding for both ports: asset class -> ordered provider ids (primary + fallback), optional per-symbol override; sync, backfill and the WS subscription manager resolve per symbol.
- R3 TradingView adapter pair (history port via scraper `get_hist` with `fut_contract=1` and a configurable bar cap; realtime port satisfying the 9-member Protocol, polled bar-close at minimum) with the scraper library isolated behind an internal client so it can be swapped.
- R4 Entitlement is config: credentials/auth token, bar cap, delayed-data flag and provider map read through `Settings` from the environment; values live only in `../pocketquant-config`.
- R5 Schedule-aware sync, retry and anomaly gating; 1d/1w for futures bucketed on the schedule's session day, never UTC midnight; crypto path unchanged.
- R6 Initial backfill of the three symbols to the configured cap per timeframe; the cron accumulates 1m forward from go-live.
- R7 Paper broker, backtest engine and performance calculator read the asset-class spec (points x multiplier x contracts, integer contracts, per-contract commission option, session-based annualization); the existing futures margin accounting is kept.
- R8 UI: the three symbols are selectable in chart, strategy and backtest dialogs; exchange badge works; placeholders are no longer Binance-only.
- R9 Tests: resolver, TradingView mappers on offline fixtures, session calendar, contract math, one end-to-end futures sync; every existing crypto test stays green.
- R10 Timezone correctness: no naive datetime crosses a boundary (Mongo reads, provider mappers, schedule math); UTC storage and arithmetic; exchange-local session times converted via `zoneinfo` (`America/Chicago` for CME) with DST handled; explicit tests for DST spring-forward/fall-back on session boundaries, holiday/half-day sessions, Sunday reopen and the session that spans UTC midnight.
- R11 UTC enforcement as a verified system-wide invariant, crypto included: `TZ=UTC` pinned in Dockerfile/compose; a startup assertion that the process timezone is UTC (fail fast); ruff `DTZ` rules plus a test that fails on naive datetime construction; `tz_aware=True` on the Mongo client or boundary coercion that raises instead of silently attaching UTC.

**Goals.** G1 fresh futures bars within one cron cycle during session hours. G2 a paper ES strategy runs a full session with correct USD PnL. G3 a 1h ES backtest reports dollar PnL and Sharpe consistent with the contract spec. G4 adding a provider is one adapter plus one config entry with zero caller edits. G5 BTC/ETH/SOL behaviour and tests are unchanged. G6 the app refuses to start on a non-UTC host and the DST-boundary test suite passes.

**Non-goals.** A real futures broker; multi-year 1m futures history (deferred, recorded below as a trade-off); Databento/IBKR adapters; tick-level fidelity beyond what the scraper offers; modelling contract roll inside paper positions; redoing margin accounting; plan-tier branching in code.

**Constraints.** Single uvicorn process (scheduler and WS feed are in-process singletons); ports in `core/domain`, adapters in `core/infra`, repositories in `core`, import-linter contracts; composite `{CODE}:{EXCHANGE}` symbols; credentials only in `../pocketquant-config`; KISS/DRY and reuse of the existing pipeline (no parallel futures pipeline); the user accepts the TradingView ToS/scraper-breakage risk and the bar-cap history limit.

## 1. Verdict

The idea is sound and the generalization the user asked for is the right shape: the adapter is the small part, and treating "24/7" as crypto's schedule rather than the system default is what makes the next asset class cheap. Two of the user's decisions are ones I argued against and still disagree with, and I have built the recommendation around them rather than around my preference: sourcing from an unofficial TradingView scraper, and accepting a history cap that defers the multi-year 1m backtest goal by years. The saving grace is that R2 and R3 make the source swappable; if the scraper breaks or the history limit bites, the exit is one adapter pair and one config line, not a rewrite. What must not be skimped on is the timezone work. The repo today silently attaches UTC to naive datetimes, reads naive datetimes back from Mongo, pins no `TZ` in any deploy file, and the chosen scraper stamps bars with naive *local* time. Adding a session-scheduled asset on top of that without R10/R11 would produce bars that look right on the VPS and wrong everywhere else.

## 3. What you should not do

- Do not branch on the TradingView plan tier anywhere. The bar cap, delay flag and credentials are settings; the user upgrades the account without a code change.
- Do not build a "futures sync job" beside `sync_1m`. Gate the existing job with the schedule; one pipeline, parameterized.
- Do not let `coerce_utc` remain the only guard. It converts a naive value into "UTC" by assertion, which is how a local-time bar from the scraper would sail into Mongo looking valid.
- Do not depend on the scraper's DataFrame for timestamps. `tvdatafeed/main.py:143` builds them with naive local-time `datetime.fromtimestamp(...)`; map from the raw epoch yourself.
- Do not poll TradingView faster than the data can change. With delayed CME data (the default on every TradingView plan until the non-professional CME add-on is bought) polling below 60s only increases ban risk.
- Do not store the schedule body per symbol as a copied blob, and do not model calendar rules as Mongo documents. Reference a `calendar_id`; the rules live behind the calendar port so a holiday update touches one place (or arrives with a library upgrade).
- Do not shift stored timestamps to Chicago wall time or add a `tz_offset` column. Persist UTC instants only; `session_date` is the derived day key.
- Do not special-case `if symbol.endswith("1!")` (or any exchange suffix) in the cascade, integrity or freshness code. The calendar is the parameter; the symbol record names it.
- Do not let the `Interval` enum keep owning periods-per-year once a second calendar exists.
- Do not route realtime through the fallback chain. Fallback is for REST history where "try the next one" is cheap; two WS providers streaming the same symbol double-count bars in `BarBuilderDomainService`.
- Do not backfill futures 1d bars by cascading 1m across UTC midnight, even temporarily. The daily bars would never match the chart the user compares against.
- Do not put a TradingView username, password or auth token in the repo, tests, docs, `.env.example` or this report.

## 4. What could be better or more efficient

Ranked by effort-to-impact.

1. **Prove the routing layer on crypto alone before any futures code exists.** Register Binance as the only provider, run the existing test suite plus one prod cron cycle, and only then add TradingView. This isolates regressions to the routing change and is nearly free.
2. **One long-lived TradingView chart session instead of per-poll fetches.** The library opens a fresh WebSocket per `get_hist`; three symbols at 10s cadence is roughly 1,000 connections an hour. A persistent chart session that consumes TradingView's `du` update frames gives sub-second bar updates from a single socket. It is more code against an undocumented protocol, so keep it as a second `ITradingViewClient` implementation behind the same interface, adopted only if polling proves too chatty.
3. **Fill the history gap once, cheaply, without changing the decision.** Databento's historical pay-as-you-go tier still exists, priced per GB, with $125 of free credit for a new account; ohlcv-1m for three symbols over two years is a few megabytes. A one-off import script into `bars` would satisfy the multi-year 1m backtest goal while TradingView remains the live source. This is the hybrid the user declined; it is listed here because it costs an afternoon and no subscription, not as a cut.
4. **Reuse the `sync_verify_cascade` job as the futures alignment oracle.** It already compares provider 5m against cascaded 5m for one symbol an hour; pointing it at ES is a zero-cost check that the session-anchored cascade is right.
5. **Expose provider status on `/health`.** Authenticated/degraded, last successful fetch per provider, and per-symbol session open/closed. Ten lines, and it turns "why are there no ES bars" from a log hunt into a glance.

## 6. Benefits

- G1-G3: the three index futures chart, paper-trade and backtest with USD-correct PnL through the same UI and pipeline as crypto.
- G4: a fourth provider, or a second provider for crypto, becomes one adapter and one JSON config entry; the user's stated expectation of "more than two providers, more than one per asset type" is met structurally, not by convention.
- G5: the crypto path is preserved because every futures behaviour is a parameter (schedule, anchor, contract spec, periods-per-year) defaulting to today's values.
- G6: the UTC invariant protects the existing crypto data too; the `coerce_utc` and non-`tz_aware` Mongo gaps found during scouting are latent bugs regardless of futures.
- The next asset class (equities, forex) is an enum member plus a schedule preset; the session calendar, cascade anchor and annualization are already parameterized.
- Exit cost from TradingView is bounded and known (see trade-offs), which is what makes accepting the scraper risk defensible.

## 7. Trade-offs

- **Multi-year 1m history is deferred by years (user decision, I disagree).** TradingView caps history at 5,000 / 10,000 / 20,000 bars by plan and states the caps cannot be extended; at roughly 1,380 1m bars per CME session that is about 4 / 7 / 14 trading days. Any strategy that needs 1m futures history for more than two weeks cannot be validated until the cron has accumulated it. The backtest goal is therefore "higher timeframes now, 1m later", not "1m now". The one-off Databento import in section 4 would close this gap for under the free-credit amount without changing the live source.
- **Scraper fragility and ToS exposure (user decision, I disagree).** `tvdatafeed` is unofficial; login breakage recurs (open issues December 2025 and March 2026; forks now rely on manual browser login or an injected auth token), and TradingView's endpoints carry no stability promise. Mitigation is structural (R3 internal client interface, degraded mode, health surfacing), not preventive. This repo already migrated away from this library once (`LIMIT_TVDATAFEED_MAX_BARS` is the fossil).
- **Delayed quotes until the CME add-on is bought.** Every TradingView plan serves CME 10-minute delayed by default; the non-professional add-on is about $9.95/month on a paid plan. Until then, paper fills on anything faster than 15m bars are fiction. This is a config flag (`tradingview_delayed_data`) and a UI badge, not code.
- **Polling, not streaming.** The first realtime adapter emits on bar-close change at a 10s cadence, so `last_tick_at` semantics and the 30s staleness watchdog need looser thresholds for this provider; per-tick volume deltas are unavailable, so `tick_count` will be 1 per poll.
- **Continuous-contract roll.** `ES1!` splices contracts unadjusted at expiry. A paper position held across a roll sees a one-time basis jump (typically a few points on ES) that a real account would not; backtests spanning a roll inherit the same artefact. Roll modelling is a stated non-goal; log the roll dates in the schedule preset so results can be read with that in mind.
- **Schedule presets in code, not DB.** Holiday updates require a code change once a year. Chosen for KISS; the value object's `schedule_code` reference makes moving it to a collection later a persistence-only change.
- **When the TradingView choice stops being right, and what switching costs.** Switch when any of these holds: a strategy needs more 1m history than the cron has accumulated; the scraper breaks twice in one quarter; the user moves toward real-money futures trading and needs licensed, timestamped data; or the CME add-on plus a paid plan exceeds roughly $25/month, at which point Databento's $199/month is buying licence certainty rather than data. The switch cost, given R2/R3 done properly, is one adapter pair (`IDataProviderPort` + `IRealtimeQuoteProviderPort`) with mappers and tests, plus one config line to change `INDEX_FUTURE`'s provider list; on the order of two to three working days, and all bars accumulated so far remain valid because the domain model is provider-neutral.
- **New dependency.** `pandas_market_calendars` enters `core/infra` for the CME calendar. It is the right trade: hand-maintaining CME holiday and early-close rules is exactly the yearly chore the user wanted to avoid, and the library already re-exports `exchange_calendars` if equities come later. Keep it behind the port so `engine` never imports it.
