## data-path-analysis (I unless marked V)
- C (strategy self-aggregates from entry stream): O(1) per bar, no I/O; look-ahead-safe by construction; best parity; HTF never matches vendor chart; warm-up needs ratio x 35 entry bars (1h->1w ~4000-5000; 15m->1w ~16000); 1-2 files.
- B' (engine reads stored vendor HTF from Mongo, hands to strategy): one indexed query per (symbol, interval) rollover when cached and shared; needs calendar-aware closed-bucket filter (V cascade partial buckets); same stored bars live and backtest; V live lag = sync schedule (daily ~3h, weekly fine) -> needs hourly HTF freshness fetch or deterministic available_at; warm-up per interval independent; 2 files + 1 job.
- A (trader routes several live interval events): V live 1d/1w buckets (UTC/Sunday) != stored vendor bars -> live != backtest for session symbols; k-way merge by bucket END in backtest; 6-7 files. Dominated.
- Owner's call: B' (A13). Trade-off note only: per-bar in-memory math is O(1); C's real cost is warm-up replay volume, not per-bar compute.
- Scale sizing for B' (I): 100 instances / 10 symbols; HTF reads = per (symbol, interval) rollover (tens/hour, ~1-3 ms each indexed); zero per-bar HTF queries in backtest (HTF loaded once per interval for the range); warm-up reads ~ (symbols x intervals) not instances; Redis snapshot writes <= 1 per instance per entry bar (100/min worst case on 1m entry); context cache ~10 x 2 x 500 bars = few MB.
